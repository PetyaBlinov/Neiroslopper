# Разработка Neiroslopper

## Рабочее окружение

Нужен Windows и Python 3.11–3.14 x64 с Tkinter. После клонирования выполните `INSTALL.cmd`, затем запускайте `START.cmd`. Установщик создаёт локальную `.venv` и устанавливает `requirements.txt`. Если рядом есть локальный `vendor/wheels`, зависимости берутся оттуда; этот кэш не публикуется в Git.

Для разработки из PowerShell:

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe launch.py
```

Программа открывается с выбранным DEMO. Сам запуск не подключает плату и не отправляет команды движения.

## Ветки

| Ветка | Для чего |
| --- | --- |
| `main` | Проверенная версия, которую можно запускать |
| `develop` | Сборка следующих изменений перед выпуском |
| `feature/краткое-имя` | Одна новая возможность от `develop` |
| `fix/краткое-имя` | Исправление одной проблемы от `develop` |

Названия рабочих веток удобнее писать латиницей: `feature/svg-preview`, `fix/tcp-timeout`.

Обычная последовательность работы:

```powershell
git switch develop
git pull --ff-only
git switch -c feature/short-name
# Внести изменение и выполнить тесты.
git add <изменённые-файлы>
git commit -m "feat: describe the change"
git push -u origin feature/short-name
```

Откройте pull request в `develop`. После проверки законченная версия попадает из `develop` в `main`. Рабочая ветка относится к одной задаче и удаляется после слияния. Это договорённость команды; наличие файла с инструкцией само по себе не включает защиту веток на GitHub.

## Проверки

```powershell
.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Набор проверяет протокол и ошибки соединения на имитаторе, TCP на `127.0.0.1`, генерацию YAML, редактор, DEMO и отмену работы. Тесты не открывают COM-порт и не управляют физическими приводами.

GitHub Actions запускает эту же команду на `windows-latest` для Python 3.11, 3.12, 3.13 и 3.14. События: push в `main`, `develop`, `feature/**`, `fix/**`; pull request в `main`/`develop`; ручной запуск. Workflow имеет только `contents: read`, не получает дополнительных секретов и не сохраняет Git-учётные данные после checkout. Зелёный CI означает проверку программы; это не испытание плоттера на оборудовании.

Для аппаратного изменения отдельно опишите плату и прошивку, фактическое подключение, отправленные команды и наблюдаемый результат. Подключение для чтения YAML, проверка DEMO и реальное движение — разные результаты.

## Что не коммитить

- `.venv`, кэш Python и локальные колёса зависимостей;
- `data`, личные автосохранения и каталоги реальных диагностических отчётов;
- пароли, `.env`, ключи, полные дампы flash и собранные бинарные прошивки;
- временные дистрибутивы, логи и настройки IDE.

Иконки `assets/*.png` и `assets/*.ico`, исходники, тесты и документация входят в репозиторий. Перед push проверьте `git status` и `git diff --cached`.
